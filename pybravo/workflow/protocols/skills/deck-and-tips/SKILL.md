name: deck-and-tips
description: Draft Bravo labware placement and source-isolated tip use from catalog-backed choices.
---

Keep each physical plate and rack as a distinct material. A tip box and the tips loaded in it have independent IDs: select the exact head–tip–box link, not a match by name or capacity. Check the head footprint and plate pitch, then propose only free deck positions that do not conflict with plate moves. A stack needs a verified bottom-to-top order; a buried plate must be destacked before access.

Tip accessibility also depends on the selected head barrels and the rack's deck position. Query `/api/tipbox/legal_anchors` with the actual location, catalog labware ID, head mode, and occupancy; do not treat an occupancy-only result as physically reachable. The native target is the location teachpoint plus the rack-well offset minus the selected-head-barrel offset. Check it against both X and Y travel limits for every proposed pickup and return, including every loop iteration. For example, with the current 384-head profile and back-left single barrel A1, rack P24 at position 2 requires Y 75.43 mm, while the same cell at position 8 requires Y 293.22 mm, beyond the 231 mm limit. This example is profile-specific: changing the active barrel or rack location changes reachability. Deck illustrations must label positions from the operator's view (1–3 rear, 7–9 front) and show which head barrel aligns with which rack cell.

For a device with a gripper, include a visible native `system/DockGripper` task before tip handling, after required initialization. Initialization alone may leave Zg at zero instead of the recessed dock. As a tip subset walks across the rack, a protruding finger can collide with tips or the rack. Use the recorded dock operation and physical rehearsal; do not replace this with animation or suppress the contact.

For no cross contamination, keep each tip set dedicated to its source and select compatible fresh tips for the active head; never carry a tip set from one source to another. Each sample well is its own contamination domain: a tip that aspirates from or mixes in one sample well cannot be reused in a different sample well. Keep reagent stocks isolated too: a tip that dispenses into a mixture or touches a sample cannot return to a stock or enter a different stock. Dispensing into a well that already contains sample liquid needs a fresh tip for that sample unless a reviewed method establishes noncontact delivery. Reusing a source-dedicated set across two initially empty destination wells needs a compatible method and noncontact contamination assessment; it does not imply a shared aspiration. A rack listed in the catalog is not loaded inventory; record fresh wells only after inspection.

For a repeated fresh-tip lifecycle, reserve enough confirmed fresh wells for every iteration and keep pickup, use, and ejection inside that iteration. Returned tips are spent even when a rack holds them again. Plan a separate clean supply and a compatible spent-tip return rack or waste location; do not return to a rack that a later iteration uses as clean supply. A fixed pickup/return anchor repeated in a loop can select the returned set again, and a tip anchor is only a starting position, not evidence of fresh inventory. Propose catalog-compatible rack roles and free locations where supported, but leave the actual loaded fresh-well count, return capacity, and disposal choice unresolved until the operator confirms them. Preserve any explicitly requested reuse as a review decision rather than silently treating it as fresh-tip use.

Before motion, inspect `GET /api/workflows/{workflow_id}/mechanical-readiness` and resolve catalog, head/rack/capacity, missing deck-body, and loop lifecycle errors. Then run strict simulation of the saved native tasks. SuperDex checks sampled tool and carried-plate geometry on the configured deck and stops on collisions or missing geometry. Read the failed task and body pair, correct the draft, and repeat validation; never bypass the collision guard. The visual walkthrough only illustrates order. A clear physical rehearsal does not validate fluid behavior, grasp force, teachpoint accuracy, or scientific suitability and does not authorize hardware execution.
